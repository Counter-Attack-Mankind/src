## A–J 核验结论

### A. 用户描述中真实发生的部分

真实发生：V0 从 A1 离场去 B21；V1 从 B31 去 A1；V0 持有普通
reservation 对应的一个 zone，V1 因 `time_brake_V0` 等待；V1 已实际进入另一个
zone；`enforceForwardClearance()` 随后令 V0 `clear_block_V1`，形成 V0→V1、
V1→V0 的环。正式状态和弧长估计均准确。

### B. 时间与 zone 编号偏差

- `5536.1 s` 是 **1:32:16.1**，不是 1:31:16。
- V0 实际在 5485.2 s（1:31:25.2）激活 TO_B，不是约 1:31:21。
- 5488.5 s 有四个 zone；5490.5 s raw0 被过滤后才是三个。
- 最终日志中的 zone0/zone1 是 active 编号；稳定编号实际是 raw2/raw3。
  `findConflictZones()` 在 `rule_engine.cpp:647-678` 复制、过滤并压入新 vector，
  因而 active 下标会变；新增 `raw_index` 不参与决策。

### C. 为什么可预测穿过蓝色 zone

蓝色仅表示完整固定路径上存在 OBB 空间重叠的潜在资源，不表示当前同一时刻会
碰撞，也不是通行许可/锁。普通 pairwise 层只在同时间采样 OBB overlap 成立后才
创建 TimedEvent。因此设计允许车辆在未被当前 TimedEvent 选中的蓝区内运动。

### D. 没有 TimedOverlap，还是只处理第一段

在 plan 2946（5488.5 s）尚无 reservation；下一 refresh 的 plan 2947 已检测到
15 s 窗口末端的 overlap。5490.5 s 并非“完全没有 TimedOverlap”：明确存在
`[14.750,15.000]`。代码只收集第一段连续 overlap，遇到段后首个 miss 即 break
（`rule_engine.cpp:1628-1671`）；已有 reservation 时也只重算第一段
（1565–1588），并在 1624 `continue`，不会再寻找后续事件。

### E. TimedEvent 关联多少个 zone

一个。首个 hit 通过最小弧长区间距离选择单个 `event.zone_index`
（1640–1661）；后续 `recordConflictZones()` 传入 `{zone}`（1750–1755），
`ConflictReservation` 也只保存这一组 enter/exit（1772–1790）。

### F. reservation 是否没有提前建立

不是“没有建立”。它在 5490.5 s、距正式环 45.6 s 时已经为 raw2 建立。
没有为 raw3 建立 reservation，是因为普通 reservation 的单事件/单区模型以及
已有 reservation 的短路；raw3 的真实占用没有被原子地并入 raw2 reservation。

### G. 2 s refresh 的作用

是，事件在 plan 2946 到 2947 之间进入 15 s horizon，并在下一次 refresh 立即出现；
因此 refresh 最多带来约 2 s 的可见性延迟。但创建时 `first_t=14.75 s`，不是临碰
前才发现。V1 恰在创建 tick 跨入 raw3，核心缺口仍是 raw2/raw3 未原子仲裁，不能
只归因于 refresh。

### H. NOMINAL 预测与执行是否漂移

代码确认存在模型差异：局部 `predict()` 从当前速度出发，但未来目标速度固定采用
`NOMINAL` 并叠加曲率限速、加减速度（`rule_engine.cpp:1314-1345`）；实际 rolling
执行的是冻结 frame 中可能为 STOP/CREEP/YIELD 的动作。因此到达时间可以漂移。
本次日志没有单独量化该漂移对首次错误决策的秒数，故其精确因果贡献为：
**未知，需要确认**。已确认的跨区单 reservation 缺口无需依赖该推测即可解释环。

### I. 正常时空通过还是遗漏原子仲裁

两层答案：进入未选中的蓝区本身符合当前时空过滤设计；但 raw2/raw3 在双方路径
区间相互重叠，V1 占 raw3 的同时又成为 raw2 waiter，随后 V0 被 raw3 的真实车身
挡住。对这一场景而言，结果暴露了普通 pairwise 多 zone 缺少原子闭包，而不是一个
安全完成的“正常通过”。

### J. 第一次真正错误决策

`tick=54905 / sim_t=5490.5`，`RuleEngine::resolvePairwiseConflicts()` 的首次事件选择和
reservation 创建路径（`rule_engine.cpp:1628-1790`）。当时 V1 已从 .273 跨到 .287，
实际进入 raw3；函数却只把未来第一段 overlap 映射到 raw2，并将 V0 设为 raw2 holder、
V1 设为 waiter，没有把 V1 的 raw3 actual occupancy 纳入同一原子资源决策。
55112 是环首次显现为双向等待边，55361 是 25 s 阈值后的正式检测，不是首个错误。

## 可视化修改

- `ConflictZone`、reservation 和 marker 增加稳定 raw index 与诊断 AABB。AABB 在
  `computeConflictZonesFull()` 使用实际 OBB intersection polygon 的 min/max 联合得到，
  不使用中心或路径端点猜测，也不参与任何仲裁。
- raw index 在完整缓存聚合完成后赋值；active index仅在显示时使用当前 vector 下标。
- `conflict_zone_aabb` 使用稳定的 pair/path_gen/raw hash ID：潜在为橙色，当前
  TimedEvent 或 reservation 选中为红色；蓝色 `potential_conflict_zone_overlap`
  不变；真实 `conflict_timed_obb_overlap` 红色 polygon 不变。
- 标签包含 pair、raw/active、双方区间、POTENTIAL/TIMED/RESERVED、holder/waiter。
- 失效稳定 ID 显式 DELETE；`show_prediction_conflicts=false` 时也删除全部旧 zone
  geometry、AABB 和标签。

实际 bag 消息检查到同一 ID 的蓝色 `TRIANGLE_LIST`、橙色
`conflict_zone_aabb/LINE_STRIP`（5 点闭合）和完整文字标签。死锁时红框与红色 timed
polygon 的路径由同一 `selected` 状态及现有 `conflicts` 数据驱动；本环境未进行可视
GUI 截图，故像素级 RViz 对比为：**未知，需要确认**。

## 滚动 bag 与回放

本机 `rosbag record --help` 没有 `--snapshot`，因此采用等价的短分片循环缓存：

- 只录 `/forklift_map/markers` 与 `/forklift_planner/markers`。现有
  `forklift.rviz` 的相关显示只订阅这两个 MarkerArray；车辆、路径、rolling horizon、
  zone/AABB、timed overlap、reservation 与状态文字均在其中。当前 RViz 配置没有 TF
  display，因此本场景不录 `/tf`、`/tf_static`。
- 默认 10 s 分片、11 个 finalized 分片加 active 分片，稳态约 110–120 s；LZ4、
  `--repeat-latched`。触发时 SIGINT 封口、归档旧窗口、立即启动新窗口。
- `FIRST-WEDGE` 在最大 wait 首次超过 25 s 时触发并在等待清空后重新 armed；正式
  deadlock 按环签名去重。deadlock 同时标记 wedge 已捕获，避免下一 tick 重复归档。
- 触发消息和目录名包含 event、seed、vehicle_count、sim_t、tick；录制/文件系统错误
  位于独立 Python 进程和 worker 线程，不传播到协调主循环。默认关闭。
- `.gitignore` 排除 `.bag`、`.bag.active` 和默认输出目录。

实测用显式 `max_splits=14` 压力验证：15 个封口分段，首包起点
1786519268.30，末包终点 1786519414.21，总窗口 **145.908 s**；首尾包都只含上述两个
MarkerArray topic。实测归档后 rolling 自动重启。完整 15 段目录在 100x、`--clock`、
`/use_sim_time=true` 下顺序播放并干净退出；单包 20x 同样通过。默认 11 的最大窗口按
同一 rosbag 分片语义约为 120 s。

完整回放命令：

```bash
roslaunch forklift_planner multi_vehicle_debug_replay.launch \
  snapshot:=~/forklift_debug_bags/snapshots/<event_seed...目录> \
  rate:=0.25 paused:=false
```

设置 `paused:=true` 后由 `rosbag play --pause` 启动，可用空格暂停/继续、`s` 单步。
回放 launch 不启动 map node 或 planner，只启动 segment replay 和 RViz。

方案比较：分片 bag 能精确还原已经发布的 RViz 消息、存储约等于两个 MarkerArray
最近两分钟、实现和运行隔离，但不能重算内部未发布状态；确定性 checkpoint 重放能
重算内部状态，却需要状态完整性、版本一致性和较高实现复杂度；组合方案诊断最强，
但本轮需求以还原现场为主，故只实现分片 bag。

## 后续建议（本轮未实现）

为普通 pairwise TimedEvent 增加多 zone 原子闭包：以首个 timed zone 为 seed，沿双方
弧长区间重叠关系求闭包，actual occupancy 优先，单个 commitment 同时保存全部区间，
释放条件取闭包的完整 clearance，并纳入 `SimSnapshot`。实现前必须分析与 Future A1、
DepartureClusterCommitment、动作保持和 `enforceForwardClearance()` 的叠加顺序，并做
固定 seed 多车 batch 回归。本 EXP 只给出建议，没有修改协调算法。
